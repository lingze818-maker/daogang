## 目的

验证 11-04 清库实验留下的假设：重启后 accepted 不落，是否因为 source 配置没有持久化。做法是把配置重新填对，再冷启动服务，然后渡一条 trigger 看链路能否走完。

## 条件与步骤

1. 面板重填 GitHub source 卡片（repository / cli 两项）。
2. `start-dsh.ps1` 一键冷启动（标准咒：读 key、杀残留、等锁、后台启动、健康检查）。
3. `pnpm dispatch` 渡一条任务经 `triggers.jsonl` 进 DSH。
4. 观察 inbox / orchestrator 计数：received、judged、accepted、evaluating。

## 结果

| 指标 | 值 |
|---|---:|
| received | 4 |
| judged | 4 |
| accepted | 1 |
| evaluating | 曾到 1 |

**端到端链条在「配置正确重填 + 重启」场景下完整走通**：trigger 被接收、评估，其中一条进入 accepted。

## 定性修正

11-04 的「重启后 accepted 卡死」不再是「疑上游状态机」问题，而是**「source 配置不持久化」的下游表现**：配置蒸发后，评估前置（admission 名单等）随之失效，trigger 被 judge 后自然丢弃；配置经面板重填即全链恢复。

## 遗留

- **配置持久化仍是上游应修的真问题**：重启/清库即丢，面板重填 30 秒只是权宜。
- **第二轮 trigger judge 后未 accept**（疑重复判定），后段 ticket/worker 观察写下轮。
- 本次只验证到 accepted；活 Session 与真实模型请求不在本次观察范围内。

## 复跑要点

- 需要面板配置与冷启动脚本都在位；跨进程桥两端须把 `DAOGANG_HOME` 指到同一路径，`triggers.jsonl` 才读得到。
- 计数以服务面板 / API 的实时值为准。这是一次性实测，不是无密钥可复跑的 bench。
