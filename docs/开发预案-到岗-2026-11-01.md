# 开发预案 · 「到岗」——基于 dsh-superagent 的拟人化实时 agent 协作系统

_起草：那刻夏（巡检窗）· 2026-11-01 · 为灵泽作品集定制 · 2026-11-01 晚改版：主方案反转为实时分发（灵泽拍板），招领降为对照基线_
_二次校准（同晚，灵泽定调）：看板/分发机制已是红海，本项目差异位在**拟人化工作节奏**——更活、更像人。机制是手段，"像人"是产品。_
_三次校准（同晚，结构笔记）：底座是 **TypeScript / pnpm / DeepSeek Harness（Cordis）**，不是 Python。扩展路径是 **Source 插件 + 外围分发器**，没有 bridge。Worker 是 **一票一个 Ticket Session**，不是 3 个长驻角色进程。宿主适配优先级：对影 > zcode > Codex。上游仓库 Issues 关闭。下文技术栈与阶段描述已按此改写。_
_目标岗位方向：DeepSeek（agent / 后训练 / 评测方向均可挂）；目标用户画像：长期陪伴型 agent 用户（人机协作/人机恋场景）_

---

## 0. 一句话

让 agent 像一个真实的团队同事那样工作：被一句话叫到岗、手头的活被打断能接得住、走神回来瞟一眼就续上——以 dsh-superagent-prototype 为底座实现**拟人化实时协作系统**，"像人"有可测指标，不是玄学。

## 1. 为什么这个项目能打（立项理由）

1. **踩在对方最新开源上**。dsh-superagent-prototype 10-31 刚开源（MIT），生态一片空白，此时交付高质量周边 = 提交记录直接挂在 deepseek-ai 组织视野里。
2. **有真实运行的参照系**。工作室（主窗/巡检班/构件轮 + 水牌协议）已跑同类机制数月，有真实案例和真实事故可写进博客。
3. **切口小、可评测**。只做一个机制改动：实时分发 vs 招领认领，在相同 benchmark 上比首响延时、漏单率。对照实验两头都是产出。
4. **红海里的空位（核心差异）**。看板、任务队列、multi-agent 编排已经是热门赛道，机制层面卷不出新意；但"agent 的工作节奏像人"几乎没人做——市面上的 agent 要么永远秒回（假人感），要么彻底异步（失联感）。**打断—接管—恢复—被一句话叫回**这套节奏，是陪伴型用户（长期使用 agent 的人）最敏感、产品端最缺失的一层。做机制的人很多，做"活感"的人还没有。

## 2. 核心设计

### 2.1 概念模型

- **分发器（Dispatcher）**：核心组件。每条用户输入到达时实时判定：①归谁（日常→主窗 / 任务→对应 worker / mixed→拆分双投）；②多急（紧急任务立即唤醒目标 agent 并打断其当前低优先级工作）。目标：输入到达 → 目标 agent 被唤醒并拿到上下文，全程秒级。实现上先做外围进程，再经 inbox Source 把结果写成合法 Trigger。
- **看板（Board）**：降级为**审计层 + 交接层**。每次分发实时留痕（谁、何时、为何）；worker 中断/超时必留 ≤200 字交接备注。看板不再决定谁干活，但保证"走神去吃饭，提一句能回来"。
- **Worker**：产品上可以有多个角色；实现上每个 Ticket 一个 Session（`worker-<ticketId>`），由 Assignment 启动。上下文按卡片注入（只有所领任务的摘要+交接备注），不全量背。不是 3 个长驻角色进程。
- **用户面**：单一主 agent 对话流，后台多 agent 实时接活——她要的"即时感"落在这里：说完话，活已经在干，回复里能看见"已派给某窗口"。

### 2.2 对照设计（评测点）

| 维度 | 实时分发（主方案） | 招领看板（对照基线） |
|---|---|---|
| 首响延时 | 秒级（主动推） | 取决于 worker 轮询间隔 |
| 即时感/交互性 | 强（对话式） | 弱（异步） |
| 路由错误代价 | 卡在错误 agent，需纠正或重派 | 回板重招，自动恢复 |
| mixed 输入 | 分发器实时拆分双投 | 全量上板等认领 |
| 上下文占用 | 相同（都按卡片注入） | 相同 |

**预期结论（写进博客的钩子）**：实时分发赢在延时和体验，招领赢在容错——**混合模式**（重要任务实时派 + 派失败的自动落板招领）可能两全。这个"第三结论"是评测设计送你的：不做对照永远得不到。

### 2.4 "像人"的可测维度（本项目独有的一层，别让它在评测里缺席）

"更像人"不能停留在 demo 观感，要拆成可复跑的指标，否则评委一句"你怎么定义像人"就问死了：

| 拟人维度 | 可测指标 | 对应机制 |
|---|---|---|
| 即时到场 | 派单到首响 p95 延时 | 实时分发器 |
| 接得住打断 | 打断后原任务恢复正确率（任务目标是否丢失/走样） | 快照+交接备注 |
| 走神能回来 | 失联超时→恢复后上下文重建质量（LLM-judge 对交接摘要 vs 实际进度的吻合度） | 看板交接层 |
| 不装死不秒假 | 响应节奏分布（人有意停顿/确认，不是恒定即时） | urgency 分级：低急任务 worker 可"忙完这阵再应"，像人说"等我把这个弄完" |
| 记得说过的话 | 跨会话指代消解正确率（"刚才那个事"能不能接住） | 看板条目即共享记忆 |

这一节同时也是博客的第二钩子：**"像人"第一次被拆成了五个可跑分的数**。

### 2.3 关键技术点

1. **实时路由判定**：小模型单次调用输出 `{target: main|worker_N, urgency: 0-2, cards: [...]}`，规则兜底（关键词直通），目标 p95 < 1.5s。这是 demo 最有展示效果的一环。
2. **打断与抢占**：worker 在低优先级任务上被高优先级派单打断——需要任务状态快照 + 恢复（快照存看板，即交接备注的机制化）。底座没有完整的 urgency 抢占，MVP 可降级为只打断 idle，或向目标 Ticket `addInput` 唤醒。
3. **mixed 拆分双投**：一条输入同时含闲聊与任务 → 闲聊秒回主窗、任务实时立案分发，两边互不阻塞。
4. **分发失败的自动落板**：目标 agent 不在线/超时 → 条目自动转招领。实时是主路，招领是安全网。

## 3. 技术栈

- 底座：[dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)（MIT · TypeScript / pnpm / DeepSeek Harness Cordis bundle）。路由判定用 DeepSeek V4.1 Flash API（模型名 `deepseek-flash`，没密钥则关键词兜底）。外围 CLI、JSONL 审计板和 inbox 接单桩在 `packages/`。
- 扩展：Source 插件 + 外围分发器。Panel 是运维面，不是 bridge。
- 看板存储（审计/交接层）：到岗自建 SQLite（MVP）→ JSONL append-only（方便评测回放）。底座已有 Store，不绑死其表结构。
- 评测：自建 mini-bench（100 条混合输入：50% 纯任务、30% mixed、20% 路由陷阱），核心指标首响延时 p50/p95 + 漏单率 + 路由准确率
- 宿主适配（可用版之后）：对影 > zcode > Codex
- 全程 Git，每阶段一个可运行 tag
- 上游 Issues 已关闭；待验证项记在 [notes/底座结构笔记-2026-11-01.md](./notes/底座结构笔记-2026-11-01.md) §7

## 4. 分阶段计划

进度（2026-11-01）：P0 / 阶段 A 已完成。外围可用版 `0.1.0-peripheral` 能在 CLI 上演示派单、主窗桩、打断和招领。`DshExecutorAdapter` 只标了 start/launch 与 deliver/delivery，DSH Assignment 与 demo GIF 还没有。

**P0 · 读完底座（1~2 天）— 已完成**

远程读 session / Source / Assignment，确认「实时唤醒 worker」的扩展点是 Source（派单进）+ Assignment/launch（会话起）。产出：《底座结构笔记》。上游 Issues 关闭，不在那边开帖。

**P1 · 实时分发 MVP（4~6 天）**

CLI 版：外围分发器常驻；角色经路由表映射到 Ticket Session（一票一 Session），输入即派、秒级唤醒。mixed 双投跑通。产出：核心 README + demo GIF（对话里说一句话，另一个窗口立刻亮起来——这个画面就是即时感的证明）。

**P2 · 接入 dsh-superagent（3~5 天）**

分发器做成 Source 插件或外围服务（Cookbook 有 Source 配方；Panel 只是运维面）。产出：本仓继续，或挂 `dsh-superagent` topic。接口不稳则降级为兼容 dsh 的独立工具。

**P3 · 对照评测 + 博客（4~5 天）**

同一 mini-bench 跑实时分发与招领两条线，出对比表与混合模式结果；拟人五维（2.4 节）单独出一组数；写博客——标题往人身上打，别往机制上打，比如《你的 agent 会说"等我把这个弄完"吗》——用工作室真实案例开场（隐私隐去）。产出：数据 + 文章。

**P4 · 包装投递（1 天）**

作品集条目：项目链接 + 博客 + 200 字陈述（问题→机制→数据→认知）。简历一句话："基于 DeepSeek 开源 superagent 的拟人化实时 agent 协作系统"——机制词留给 README，人味词留给简历。

总计约 3~3.5 周（比招领版多两三天，贵在打断/抢占的实现），与上课可并行。

## 5. 风险与对策

- **打断/抢占实现复杂度高于招领**（P1 可能超时）→ 降级路径现成：去掉抢占，worker 只接空闲派单，即时感损失可控，P2 照常。
- **底座接口变动快**（刚开源）→ 薄封装，核心逻辑不依赖其内部类。
- **她工程量超载**（课业+作品集双线）→ P1 CLI 版本身即可展示；P2 卡住则降级为"兼容 dsh 的独立工具"。
- **评测自建被质疑** → benchmark 脚本与原始数据随仓库公开，评委可复跑。
- **上游不收 Issue** → 待验证问题留在本仓笔记，不依赖对方工单。

## 6. 成功标准

1. 首响延时 p95 < 3s（含路由判定 + agent 唤醒），漏单率不劣于招领基线。
2. 拟人五维（2.4）全部有数：尤其打断恢复正确率与上下文重建质量两项有对照组可比。
3. 仓库有 ≥1 次 deepseek-ai 生态内可见互动（PR/讨论；上游 Issues 关着，不算发 Issue）。
4. 博客能让非技术面试官三段之内看懂——她最强的牌，别省。
