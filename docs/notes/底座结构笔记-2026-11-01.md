## 2. 领域模型一句话 + 名词映射

**一句话**：Source 产出不可变 **Trigger** → 落入 **Thread** → **Eval**（准入 Gate + 研判 Assessment）决定是否开 **Ticket**（带 **Mandate**）→ **Assignment** 绑定 **Executor**（一票一 `worker-<ticketId>` Session）→ 结果经 **Channel** 写回 Source；**Subscription** 把后续消息扇出到已接单 Ticket，人跟帖可无 Eval 续跑。

| 底座名词 | 含义（极简） | 「到岗」假设映射 |
| --- | --- | --- |
| Source / Trigger | 事件流 / 一条不可变事件 | 用户一句话输入 = Trigger；本地 CLI / 对影 / zcode 各做一个 Source 或统一「inbox」Source |
| Thread | 有序 Trigger 流，Eval 串行 | 主对话窗 ≈ 主 Thread；任务跟帖 Thread |
| Main Session（orchestrator） | 主 Session：评估、接单、派工、对外回复 | **分发器大脑**的宿主位（或旁路：外围分发器只产出路由结果，仍由主 Session/Engine 落 Ticket） |
| Eval / Mandate / Ticket | 是否开工、授权、工单 | 「派单」落地物；到岗 urgency/卡片应对齐 Mandate.scope + Ticket Inputs，而不是另起一套工单库（MVP 可双写审计板） |
| Assignment / Executor / worker Session | 派工绑定；执行器端口；`worker-<id>` | **到岗 worker**；「会话起」= `executor.start` → Effects `launch` |
| Subscription / Fan-out | Ticket↔Thread 多对多；订阅扇出 | 打断后续跟帖进原 Ticket；走神回来靠订阅 Thread + 看板交接备注 |
| Panel / Store | 监督 UI；SQLite 持久化 | Panel = 人看的运维面；Store 事件 ≈ 招领/审计板的事实源；到岗自建板可订阅 DomainEvents |
| Passes / Effects | 2s 一轮 + 入站立刻 request；持久副作用队列 | 近实时泵；**非**子毫秒总线——秒级体验要压在「入站→request→launch」路径上 |

## 3. 消息 / 事件：从入到执行的路径

```
Source 插件循环 (github.ts / feishu.ts / 未来 webhook…)
  → SourceContext.receive(trigger)          # src/sources/host.ts
  → Passes.receive                          # src/app/passes.ts：engine.receive + request()
  → Engine / Intake.receive                 # src/core/intake.ts：去重、scope 过滤、Thread、扇出、queueForEval
  → Passes.pump → effects.kick + Engine.evaluateDue
  → Evals + Assessor（inferred 要主 Session 研判；explicit 可直接 decide）
  → Engine.decide(accept) → Tickets 建 Ticket/Mandate/Assignment/Subscriptions
  → Executor.start → Effects「launch」      # src/executor/dsh.ts + src/app/effects.ts
  → 建/复用 worker Session、prepare 目录、投首条 assignment 消息
  → 后续 Input → Effects「delivery」唤醒 idle worker
  → Channel 回复：Outbox → SourceRegistry.send
```

关键真实路径：

- 入站入口：`Passes.receive` / `SourceContext.receive` → `Intake.receive`
- 评估推进：`Engine.evaluateDue`（Passes 每 2s + 入站立刻）
- 接单写域：`Engine.decide` → `Tickets`（`src/core/tickets.ts`）
- 会话起：`DshExecutor.start` / `deliver`（`src/executor/dsh.ts`）
- 主插件装配：`Runtime`（`src/app/runtime.ts`）暴露 Cordis 服务名 **`orchestrator`**（类型 `SourceHost`）
- 角色入口窄接口：`EngineForSources` / `EngineForMainSession` / `EngineForExecutor`（`docs/007-architecture.md`）

## 4. 实时唤醒 worker：候选扩展点

### 扩展点 A · 新 Source kind（推荐主路 ·「派单进」）

- **在哪**：`SourceKind`（`src/sources/kind.ts`）+ 插件 `apply` 注册到 `ctx.orchestrator.sources`；Cookbook 完整配方在 `docs/008-cookbook.md`（webhook 示例）。
- **怎么挂**：实现 translate→Trigger、`scope`、`channel`、`policy`、轮询/推送循环；`package.json` exports + `cordis.patch.yml` insert；配置开实例。本地 CLI / 对影消息都可做成「inbox」Source，稳定 Trigger id，cursor 进 `KV`。
- **风险**：默认路径仍走 Eval（延时与模型成本）；要「秒级到岗」需 Policy 配成 **explicit 直通**（名单 + @/addressed）或接受后几乎立刻 `decide`，避免 inferred 卡在主 Session 研判。Issues 仓关着，上游接口变了只能 fork 自保。

### 扩展点 B · Intake/Passes 入站 + Tickets.wake / Assignment launch（「会话起」硬钩子）

- **在哪**：`src/app/passes.ts`（`receive`→`request`）、`src/core/intake.ts`（扇出后 `tickets.wake`）、`src/core/tickets.ts`（`addInput` / `wake` → `executor.start`）、`src/executor/dsh.ts` + Effects `launch`/`delivery`。
- **怎么挂**：不要改 Engine 私有规则；**外围分发器**只做路由与卡片，真正落单仍 `receive` 合法 Trigger 或走主 Session 工具 `decide`/`attach`。打断 = 向目标 Ticket `addInput`（高优文本/trigger）触发 `delivery`；抢占语义需自建（底座有 slot/优先级雏形：人消息可超 `maxWorkers` 一槽，但无「urgency 0–2 抢占低优任务」）。
- **风险**：Passes 2s 定时是兜底；热路径靠 `request()`。改 `Intake`/`Tickets` 内部 = 违反薄封装，升级必碎。`WorkerSlots` 与 pause 会让 launch 变 `Later` 重试——评测 p95 要计入。

### 扩展点 C · 外围服务 + Panel/Management HTTP（降级 / 对照招领）

- **在哪**：`src/app/http.ts` + `src/app/api.ts` + Panel（`src/client/*`，docs/005）；哲学与运维面已齐，**不是**进程内 bridge。
- **怎么挂**：分发器独立进程，经已有 Management API / 自建旁路写审计板；失败落「招领」只写到岗自有 SQLite/JSONL，必要时再投 Trigger。挂 dsh 生态用 Cordis 旁路插件，只依赖 `SourceHost`。
- **风险**：HTTP 偏监督与设置，不是低延时派单总线；双写（Engine Ticket ↔ 到岗板）易漂。预案初稿写的 panel/bridge 先例 → **应改口为 Source 插件 + 可选外围服务**。

### Top 3（执行选型）

1. **自建 inbox Source**：所有宿主消息先变成 Trigger（派单进）。
2. **接单后靠 Assignment/launch/delivery**：会话起与续跑（会话起）。
3. **分发器先外围**：Flash 路由 + 打断/mixed 自研，经 Source 注入；站稳再考虑 Cordis 内嵌。

## 5. MVP 边界建议（单输入流 · Ticket Session · SQLite 审计看板）

| 能力 | 贴底座 | 必须外围自建 |
| --- | --- | --- |
| 单输入流 | 一个自定义 Source 实例 = 一条输入流 | CLI/对影 stdin 适配、鉴权 |
| Worker | `maxWorkers`/并发槽；每 Ticket 一 worker Session | 产品层的角色池与路由表自建。底座是**按票建 Session**，不是 3 个长驻角色进程 |
| 实时路由 Flash | 可借用主 Session / 小模型调用习惯 | **Dispatcher** 本体、`{target,urgency,cards}`、关键词兜底、p95 目标 |
| mixed 双投 | 可拆成两个 Trigger 或 accept+主窗 reply | 拆分策略与互不阻塞的编排 |
| 打断恢复 | Input 投递、restart/recovery note、Subscription 续聊 | urgency 抢占、≤200 字交接备注 schema、拟人节奏（刻意延迟） |
| 审计看板 SQLite | 可只读/镜像 DomainEvents + Store 语义 | **到岗自有表**（派单理由、urgency、交接备注、评测回放 JSONL）；勿直接依赖 Store 私有 schema |
| 招领安全网 | Ticket 失败/blocked 阶段可对照 | 「派失败自动落板招领」状态机 |
| Panel | 监督与健康 | Demo GIF 主叙事仍应用「另一窗口立刻亮」自有 UI/CLI |

结论：**MVP 先做外围分发器 + inbox Source 注入 + 薄审计板**；阶段 C 再做成 DSH 插件。角色池与底座「一票一 Session」不一致——产品层保留角色，实现层用路由表映射到 Ticket/Session。

## 6. 不能依赖的内部类（薄封装原则）

只依赖文档化端口与插件面；下列视为内部，**禁止**业务代码 import 或反射调用：

- `Engine` 内部 parts 的私有方法与不变式（`Intake`/`Evals`/`Tickets`/`Assignments`/`Replies` 的非端口逻辑）
- `Store` 表结构、迁移（`src/app/migration.ts`）、`KV` 键名细节（可自建键家族，勿抢保留名）
- `Runtime` 构造顺序、锁、`quiet`、私有 `sourceDeps`
- `MasterAssessor` / `Sessions` / `Effects` / `Outbox` / `DshExecutor` 的私有队列与重试状态
- `src/app/tools/*`、`src/client/*`、GitHub/飞书 Source 实现细节（`github-*.ts`/`feishu-*.ts`）
- `proper-lockfile` 锁协议、health 保留名（`runtime`/`worker`/effect kinds/`sync:`）

**允许依赖的薄面**：`SourceHost` / `SourceContext` / `SourceKind` / `SourceRegistry` 公开法；`docs/001` 术语；`ReceiveResult`；Cookbook 登记方式；DomainEvents 名字（若有稳定订阅点再挂，否则只读 Store 视图 API）。

## 8. 阶段 A 结论（可独立阅读）

底座是 **DSH 上的 TS 工单编排器**，不是 Python agent 框架。到岗要的「一句话叫到岗」应对齐 **Trigger→Ticket→worker Session**；扩展主路是 **Source 插件（派单进）+ Assignment/launch（会话起）**，分发智能与拟人五维先放外围。招领看板对照 = 自建审计板 + 派失败回落；Panel 是运维面不是 bridge。本笔记已在公开仓。阶段 B 的 CLI 走外围 Dispatcher + 本地 inbox。Cordis 仍不是必装依赖。可选 `DAOGANG_DSH_ROOT` 时，适配器只调用克隆里 `DshExecutor` 的公开 `start` / `deliver`，effects 仍是站位。`effect` 表可以经由未启动的 `Effects` 留下行，卡片停在公开 prompt 文本，见 §10。空配置的 `Runtime` 在能解析 `await using` 的 Node 上会停在 `setupPending`，并且不 `effects.start()`。票夹具齐全时，私有 `launch()` 会把卡片交给 stub `sessions.prompt`。夹具配置下 `configured()` 为 true 时，同一个 `Runtime` 会 `effects.start()` 并桩住主会话 `ensure`。公开 `SessionStore.create` 能得到同一 id 的内存 `Session`；`SessionController` 仍硬挡，没有它管的活 Agent，也没有真实模型请求。`configured()` 在空 GitHub 配置下为 false，见 §7 第 7 条。细节在 §10。

## 9. 交叉核对 · 2026-11-02

来源是构件轮 2026-11-02 班笔记，和本文 2026-11-01 的记录对过。这里只收还没写清、并且不推翻上文的点，不是把那份班笔记整篇收进来。

班笔记里「P0 已经销掉、下一步只跑 `pnpm check`」和「主战场改 `prompts/*.md`」不采用。外围可用版 `0.1.0-peripheral` 与 HostAdapter（#6、#7）已经在 main。底座仍是 TypeScript / pnpm / DeepSeek Harness，不是 Python。

### 路由已经有，不要再造

上游 `prompts/dispatch.md` 的 `orchestrator_route` 已有 accept / attach / stop / ignore。attach 的纪律很严：必须显式引用那张 ticket 的 PR、Issue 或 acknowledgement；主题相似不算 attach。`handed_back` 是 worker 超出范围时退回，成为带标记的新 candidate，相当于「回板重招」。mixed 拆分在底座里已有半成品，缺的是「闲聊秒回主窗，同时把任务派出去」。到岗外围的 mixed 双投补的是这一缺，不是重做 accept / attach。

### 相对底座的三个真空位

1. **实时唤醒。** 现在是 Source → candidate → 批量评估，不是事件直通到 worker。
2. **打断与抢占。** 全库没有 interrupt。高优先级打断低优先级，加上快照、交接备注和恢复，是到岗的主实现。对影宿主这一期只另开映射、不抢窗口，见 [HostAdapter 笔记](./HostAdapter-对影-2026-11-01.md)。
3. **拟人节奏。** 底座偏向「少占注意力」的批量超时，没有按 urgency 分级、说「等我把这个弄完」的响应。

### 对照实验基线

底座默认的 candidate 批量评估，加上 attach / `handed_back`，就可以当作招领基线。评测跑「原生模式 vs 实时分发模式」两套配置即可，不必再自建一套招领基线。阶段 D 按这个理解，见 [TASKS.md](../TASKS.md) D2。

### 扩展面

Cookbook Source（上游 `docs/008-cookbook.md`）仍是官方扩展面。改 prompts、再加少量宿主，是以后可选的深化，不是当前主路径。MVP 已经走外围分发器：路由、打断和 mixed 在外围做，再经 Source 注入。prompt 深改不替代这条路径。

### 为什么适配器仍然是站位

`DshExecutor.start` / `deliver` 只调用宿主给它的 `effects.enqueue`。载荷分别是 `{ ticketId, assignmentId }` 和 `{ ticketId }`。适配器（`packages/dispatcher/src/dsh-load.ts`）自己提供这对方法，记在内存里，不打开 `Store`。业务代码不 import `Store` 或 `Engine`。站位队列因此写不进 `orchestrator.sqlite`。

写进真表的公开路径不需要 Cordis，也不需要 `Runtime`：

1. `new Store(临时库路径)` 会建 `effect` 表。
2. `new Effects(store, healthBoard)` 之后不要调用 `Effects.start()`。
3. `new DshExecutor(host)` 会 `handle('launch')` / `handle('delivery')`。handler 登记了，但 `start()` 之前 `dispatch` 直接返回。
4. 再调用公开的 `start` / `deliver`。`enqueue` 在调用当场 `INSERT`。

探测在临时库里看到两行：`launch` 的 key 是 assignment id，`delivery` 的 key 是 ticket id，`attempts` 都是 0，`Effects.pending` 为真，`sessions.ensure` / `sessions.prompt` 的调用次数是 0。

不调用 `Effects.start()` 是故意的。handler 一旦跑起来，库里没有对应的 pending Assignment 时，`launchQueued` 直接 return，成功的行会被删掉，刚写下的痕迹就没了。票、Assignment 和 workspace 都齐全时，同一个 handler 会进入私有 `launch()`，接着 `sessions.ensure` 和 `sessions.prompt`。那一步要活的 DSH Session，本探测不做。

### 卡片停在哪一层

effect 载荷没有卡片字段。探测确认行里的 JSON 不含卡片摘要。

worker 首条消息是私有 `launch()` 拼出来的，再交给 `sessions.prompt`。它用到的公开函数是：

| 公开函数 | 它读什么 | 探测 |
| --- | --- | --- |
| `triggerMessage` | Trigger.`text`（以及线程、作者、时间）。不读 `meta` | inbox 把本腿卡片附在 `text` 末尾，标记 `[daogang-cards]`。函数返回的 `text` 仍含摘要，且没有被 600 字上限截断 |
| `ticketExecution` | explicit 时，accept 结果的 `note` 变成 `execution.assignment` | 把同一段卡片文本放进 `note`，`assignment` 里还有摘要 |
| `inputMessage` | `kind: 'text'` 的输入原样返回 | 续跑文本带着卡片块，返回值不变 |

`meta.cards` 一并写上，并且能经 `store.triggers.save` 再读出来。底座核心不解释 `meta`。只放在 `meta` 里的卡片，私有 `launch()` 不会抄进 prompt。

所以这一步把卡片送到了「随后会被 prompt 消费」的文本，没有送到一次真实的模型请求。
